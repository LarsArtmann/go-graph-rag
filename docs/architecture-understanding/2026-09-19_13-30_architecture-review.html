00Summary

The SDK is a single Go package with nine files that each own exactly one concern: model (graph.go), vector math (vector.go), indexing (build.go), retrieval (search.go), provider seam + two implementations (embed*.go), persistence (store.go), configuration (config.go). Dependency direction is clean: the domain files import nothing but stdlib slices/sort/time; all infrastructure (net/http, database/sql) lives in exactly two files. The two extension points that consumers actually need — Provider and Cache — are interfaces, and the two scaling seams the future needs are already designed in the binding ADR (docs/planning/2026-09-16_13-25_seam-store-search-adr.md).

The only weak dimension is scalability, and it is weak by recorded decision: the pairwise paths are quadratic (measured 369.5 ms per 1,000-doc build, ~15 min extrapolated at 50k nodes, bench_test.go), the owner has confirmed the corpus stays far below that trigger until ~2027-09, and the ADR names the exit (VectorIndex/GraphStore seams + adapter modules). Scaling work now would be YAGNI. What is NOT YAGNI: three constant-factor speed levers that make every corpus size faster without touching the API contract, and two hardening fixes where the code is softer than its own documentation claims.

The bottom line Do not restructure. Land the three speed levers (concurrent embed batches, parallel pairwise scan, normalized-dot fast path), harden the two seams that are softer than their docs (cache-error policy, Searcher aliasing), and promote the ADR’s interface sketch into a compile-only test so the designed future cannot rot. That list is the whole distance to superb.

◆What is already excellent

+
Seams exist exactly where consumers need them Provider (embed.go:32) and Cache (store.go:60) are small interfaces with two real implementations; Build is a pure function and the Searcher is documented immutable — tests inject fakes without mocks.
+
Determinism is a feature, not an accident Every sort has a total key (score then ID; weight then target), renders are byte-stable, and golden tests pin it (hardening_test.go:269, :294). This is what makes the parallelization in this report provable.
+
Dependency austerity is measured, not vibes 31 modules in a consumer graph (ADR §6); the metaengine alternative would have made it 205. The flat root-package layout is a recorded owner decision with the tradeoff written down (AGENTS.md, 2026-09-15).
+
The rebuildable-index promise is enforced by structure One SQLite file, one writer, embeddings namespaced by content hash × provider × model (store.go:22-30); losing the store costs a rebuild, and the cache makes that cheap. Health/shutdown duck types make the store a honest citizen in DI containers (store.go:122-141).
+
The future is already designed The seam ADR fixes VectorIndex/GraphStore, the three backend classes, CGO-in-adapters-only, and the trigger-gated adapter plan. This review endorses it as-is; nothing here competes with it.

01Findings

Ordered by impact. Every finding cites code read this pass.

Important · silent degradation

Cache read errors are swallowed; write errors are fatal — an undocumented asymmetry

build.go:206-217 (lookupCache) vs build.go:190-194 (PutEmbeddings)

lookupCache collapses error and miss into the same return nil, false. A corrupt or locked store turns every build into a full re-embed (real money on a hosted endpoint) with zero signal to the caller — while the corresponding write path fails the whole build. The two halves of the same cache enforce opposite policies, and neither is documented. 

// build.go:211-214 — read errors vanish:
cached, ok, err := cache.CachedEmbedding(provider.Name(), provider.Model(), hash)
if err != nil || !ok {
    return nil, false // error == miss, silently
}
Fix: pick one policy and make it visible Either propagate a wrapped cache-read error (fail fast, matches the write path), or count degraded lookups on BuildResult (e.g. CacheErrors int) and document the degrade-to-reembed semantics. Owner-taste decision; either is ~15 lines.
Important · contract softer than docs

Searcher immutability is by convention: caller maps/slices are retained, not copied

search.go:85-93, search.go:108-115

The docs promise “immutable and safe for concurrent use”, but NewSearcherWithOptions stores the caller’s vectors map and DocumentKinds slice by reference. A caller mutating either after construction (or two goroutines constructing while one mutates its input) is a data race the type system will not catch. For a public SDK whose headline property is safe concurrency, the defense should be structural.

Fix: clone on construction, or document the aliasing Cheapest correct: copy the map and clone the slice in the constructor (~6 lines, one allocation per searcher). Alternative: document “inputs must not be mutated afterward” on both constructors. Cloning is the better contract for a v0 library that promises immutability.
Important · speed (network-bound)

Embedding batches are strictly sequential — cold builds pay RTT × batch-count serially

embed_openai.go:163-172 (Embed loop)

One 50k-document cold build is ~782 HTTP requests issued one after another. Every batch waits for the previous round trip. For any hosted provider this is the dominant end-to-end build cost — not cosine math. The retry/backoff machinery is already per-batch, so batches are trivially independent.

Fix: bounded concurrency, opt-in, stdlib-only Add EmbeddingConfig.EmbedConcurrency (default 1 = today’s behavior), fan batches over a small worker pool (channels + WaitGroup, ~40 lines, no new dependency — the dep budget is non-negotiable). Preserves input order by index-slotting results. 429 pressure is already handled by the retry path; document that concurrency multiplies in-flight requests.
Nice to have · speed (CPU-bound)

The quadratic paths are single-goroutine — a deterministic parallel scan is nearly free

build.go:273-297 (similarEdges), search.go:194-205 (SimilarPairs)

Both hot loops partition cleanly by row index i. The existing comparators are total orders (appendRanked: weight then target, build.go:328-334; SimilarPairs: score then A.ID then B.ID, search.go:207-217), so a shard-by-i worker pool with a deterministic merge produces byte-identical output — the golden tests already prove the property that makes this safe. Expected: near-linear in cores on the measured 370 ms/1k path (bench machine: Ryzen AI MAX+ 395).

Routed to ROADMAP Theme 1 rather than TODO: the owner’s 2026-09-15 corpus decision (NO until ~2027-09) makes this fuel, not fire.

Nice to have · speed (owner-gated)

Cosine recomputes both norms for every pair though every stored vector is already normalized

vector.go:97-115 vs embed_hash.go:72, embed_openai.go:333

Every vector entering the corpus is L2-normalized at construction (hash provider and OpenAI path both call Normalize()), yet the pairwise hot loops pay the full three-accumulator float64 cosine — ~3× the arithmetic of a pure dot product. An internal dot-of-normalized fast path is the single biggest CPU constant factor available. The catch: scores shift in the last decimals, which is user-visible (thresholds, %.2f renders, golden pins) — an API-visible micro-change on a shipped v0.2.0. Owner decision; pair it with a documented “vectors are normalized on ingest” invariant.

Nice to have · micro

Every cache-miss document is SHA-256 hashed twice per build

build.go:163 and build.go:197 (resolveVectors)

HashText(doc.Text) runs once while classifying misses and again when assigning fresh vectors. One extra full-text hash pass per cold document. Trivial fix: record hash-by-doc-ID during the first pass and reuse it. Pure cleanup; no behavior change.

Note · recorded policy, not a defect

Flat single-package layout — deliberate, and cheap to reverse

repo root · owner decision 2026-09-15 (AGENTS.md)

The buildflow linter’s 8 root-package findings are accepted policy for a v0 SDK. The reason this is safe: the file seams already map 1:1 to future packages (graph, vector, embed, store, search, build), and the ADR fixes the eventual module layout (core + adapter modules). Modularization later is a mechanical go.mod split, not a rewrite. Do not restructure now.

02The speed levers, ranked

Current measured truth (bench_test.go, benchstat protocol, ±1–2%): Build/1k = 369.5 ms, Search/1k = 948.6 µs, SimilarPairs/1k = 391.1 ms, StoreRoundTrip/10k = 197.4 ms. Persistence is not the bottleneck; pairwise cosine compute is.

What NOT to do now Do not pull an ANN library into core, do not add golang.org/x/sync for errgroup (hand-roll the ~40-line pool; the 3-dependency budget is a marketed constraint), and do not restructure into sub-packages — all three would spend real risk on problems the corpus will not have for a year.
