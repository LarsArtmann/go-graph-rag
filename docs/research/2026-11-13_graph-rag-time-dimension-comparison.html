00Verdict

The two designs are not rivals: they answer the same question with different products over the same repositories. Design A (cvagent) is a portfolio-knowledge projection — skills, evidence, and activity folded from an existing event-sourced journal. Design B (Atlas) is a code-content RAG — files, docs, commits, and dependency edges embedded for semantic retrieval on the go-graph-rag SDK. The real disagreement is retrieval philosophy: deterministic graph-first queries versus embeddings-first hybrid search.

Metaengine is the missing middle both designs converge on: graph adjacency ADTs, filtered vector search, and event-fed projections behind one engine-swappable planner — while go-graph-rag keeps the RAG semantics metaengine deliberately lacks (embedding providers, similarity derivation, hybrid ranking, LLM-ready rendering). This extends, and stays consistent with, the standing complementary-layers and adopt-neither-into-the-SDK verdicts of 2026-09-19 / 2026-11-10.

The bottom line If one ships, ship the cvagent route first (cheaper, decisive, existing dashboard surface); the Atlas content layer is the differentiating second act. But this is a fresh same-day split brain — an explicit ownership ruling is needed before either starts.

02Design A — cvagent: the projection

Core insight, in the doc's own words: this is a projection problem, not a RAG problem. Classic GraphRAG stacks exist to extract entities from unstructured text; cvagent's journal already contains a typed, evidenced entity-relation graph (repositories, skills, authors, fact evidence with confidence). The graph is one more read-model projection, rebuilt by replay like everything else. No LLM entity extraction needed.

Time semantics: bitemporal, for free

Axis Source Meaning
Valid time commit timestamps in evidence when the work actually happened
Transaction time journal entry timestamps when the agent learned about it (provenance; survives repair replay)

Proposed data model

type GraphEdge struct {        // Demonstrates | CoOccursWith | Authored | CollaboratedWith
    From, To      string
    Weight        int
    FirstSeen, LastSeen time.Time   // UTC — evidence-bounded skill lifespan
    Buckets       map[string]int        // "2026-10": 12 — same keys as CommitsByMonth
}

Commit nodes never materialize individually — they collapse into edge bucket weights, keeping the graph at hundreds of nodes (canvas-renderable). Author date over commit date (rebases distort commit dates); UTC at every boundary.

The one real gap

Gap · admitted by the doc

The journal discards individual commits

internal/domain/run.go · GitHistoryCollected

Only aggregates survive (CommitCount, UniqueAuthors, CommitsByMonth, TopFiles); per-commit data lives solely as fact evidence. The recommended fix is a new add-only event scan.commit_activity_collected carrying bounded per-month × per-author × per-file-skill buckets, so the graph stays replayable from the journal alone. Direct repository reads are rejected as a shadow truth.

Retrieval & presentation

Graph-first retrieval is the offline default: deterministic typed subgraph queries answer "what did I build with Go in 2023" with no embeddings at all. Embeddings are opt-in fuzzy recall only (OpenAI + chromem-go), feeding cvagent ask. The presentation rides the existing dashboard: read-only GET /graph + /graph.json?from=2023&to=2024&skill=go, Cytoscape.js as a committed static asset, time-slider brushing, as-of snapshots, T1→T2 diffs, and skill-lane timelines.

Why this design is strong It reuses already-collected typed data, keeps the graph tiny, honors every standing house convention (read-only web, add-only events, metaengine read models, offline-first), and lists explicit open questions for the owner.

03Design B — Atlas: the content RAG

Premise: a new consumer repo (working name atlas) on top of the go-graph-rag SDK, with zero core changes — the hook is already there: NodeAttrs.PostedAt *time.Time (graph.go:52). A harvester CLI walks every repo and produces documents plus caller edges in three tiers.

Tier 1 — ecosystem graph (event time in the graph)

Node kind Embedded text Time carrier
projectREADME summaryrepo first-commit date
filesource/head (filtered)last-commit date via git log -1 -- path
docADRs, CHANGELOG, TODO_LISTdoc mtime from git
commitsubject + bodyPostedAt = author date, Location = short hash
personhub, no vector—

Caller edges: project—contains→file/doc, commit—touches→file (from git log --name-status; vectorless, so cheap), commit—authored_by→person, and the killer edge: project—depends_on→project from go.mod requires — the ecosystem's real dependency web. The SDK then auto-derives similar_to edges across everything, giving a cross-repo semantic map; SimilarPairs doubles as a cross-repo duplication detector.

Tier 2 — time queries without touching the SDK

SearcherOptions has kind filters but no time filter; the design wraps the Searcher (the CV decoration pattern) and post-filters hits on PostedAt ∈ [since, until]: 

$ atlas search "event store error handling" --since 2026-09

Tier 3 — time travel via as-of rebuilds

Full bitemporal attrs would explode node count with per-blob file versions. Instead: atlas build --as-of 2026-09-01 checks out that date into a git worktree, builds a second graph into its own SQLite file (Store is one graph per DSN), pointing Build's Cache seam at the shared long-lived cache DB so unchanged texts re-embed nothing. "What changed" = node-set diff between snapshots.

Admitted weakness Everything routes through vector ranking: the Tier-2 decorator can only re-rank cosine hits, it cannot enumerate ("all activity in 2023" is not a first-class query). §05 shows the fix.

Scale guard: similar-edge derivation is pairwise over embedded nodes — ~30 repos × files plus selective commits (doc/config-touching, merges, releases, or a 12-month window) keeps the corpus in the ~5–10k embedded-node sweet spot.

A
Where Design A wins The projection insight is the better architecture given cvagent exists (scanning and fact extraction already done and typed); deterministic-first retrieval answers precise time questions without embeddings; bucket collapse keeps the graph renderable; bitemporal provenance and replay discipline arrive free; it is more decisive overall.
B

Verdict Complementary lenses over the same repositories, linkable on repo IDs. Neither subsumes the other: A cannot answer "which projects discuss the same pattern"; B cannot answer "skill lifespan with evidence and confidence".

05The metaengine synthesis

Asked how go-cqrs-lite/metaengine relates, the answer is: more than expected — it already implements both halves of the storage story the two designs hand-roll separately, plus the projection discipline Design B conceded it lacked.

Relation to each design

To Design A: its Option A is a metaengine projection. One refinement the doc misses: the Graph ADT edge is adjacency+weight only (Edge{From, To}, deliberately label-free) — FirstSeen/LastSeen/Buckets cannot ride the ADT edge; they belong in a planned collection keyed by (from, to), with the ADT kept for traversal. Two structures, one engine.

To Design B: metaengine is the concrete instance of go-graph-rag's own seam ADR (2026-09-16, scenario B of the dgraph research — and dgraphengine exists, closing the loop that research opened). A graphrag-metaengine adapter module would implement the pluggable store/search seam with an engine family instead of one bespoke SQLite schema. Two more relations: the metaengine I/O rule (all durable data I/O through metaengine) makes the adapter the legal bridge, not a nicety, for any system-based host; and VectorFilterBackend applied before ranking turns Tier-2's post-filter hack into a native filtered query — fixing the enumeration weakness.

What it does not replace

Standing verdict, re-confirmed Per 2026-09-19_metaengine-graph-vector-comparison.md: complementary layers, not competitors. go-graph-rag keeps the RAG semantics metaengine has no opinion about — the provider seam + content-hash embedding cache, similar-edge derivation, hybrid ranking policy, RenderContext, SimilarPairs. metaengine is substrate; graphrag is the semantic layer on top.

Caveats: adopt-neither-into-the-SDK held on 2026-11-10 (decisive gaps #1 ANN, #7 rich graph edges still open); per-engine modules carry EXPERIMENTAL stamps; a system-based consumer pays the measured dependency tree (184 modules / ~8 MB binary, no slim path — 2026-11-11 quantification); and at the current ~5–10k-node corpus the SDK's own SQLite store is sufficient, so the adapter is justified by engine ambition or a system-based host, not by scale today.

06The converged architecture

Metaengine is the missing middle that converges both designs onto one substrate — durable journal + projections + graph + vectors — leaving the top layer as the only real product difference:

git repos → journal / harvest events → metaengine substrate
(graph ADT · vectors · projections) → skill lens
(cvagent dashboard) + content lens
(go-graph-rag hybrid search)

Even if only Atlas ships, it should adopt Design A's journal-first discipline — durable harvest events projected into the graph, instead of re-walking git on every rebuild — which makes transaction-time provenance free on that side too. The two lenses link on repo node IDs.

1

cvagent: pure fold + graph export --json

The data contract, fully spec-able, zero UI risk.

2

cvagent: commit_activity_collected event

Unblocks per-author/per-month edges; one new add-only event type, replay restores everything.

3

cvagent: dashboard page + JSON endpoint + timeline brushing

The first product: the portfolio graph with the time dimension, on existing surface.

4

Atlas: content layer on go-graph-rag (+ metaengine adapter only if triggered)

The differentiating second act: embeddings over file/doc/commit text, dependency web, cross-repo similarity. Adapter per seam-ADR triggers, not before.
